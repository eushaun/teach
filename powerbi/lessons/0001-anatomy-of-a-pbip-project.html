Lesson 1 · PBIP / TMDL / PBIR

Anatomy of a PBIP Project

What the agent is actually writing when it "builds a report" — the file map every later lesson (and every PR review) hangs on.

Why this lesson (your mission)

In your repo, merging to main deploys to production. You review agent PRs today by looking at the rendered report; this lesson gives you the map to review the diff instead. Every specimen below is a real file from powerbi-pbip — nothing is contrived.

Your win for today: given any file path from a PBIP project, say (a) which layer it belongs to — model or report — and (b) what kind of change a diff there implies.

1 The one mental shift

A PBIX is a zip archive: report + model + imported data, in undocumented binary encodings. You can open it, but git can't diff it and no one can review it.

A PBIP is the same objects saved as a folder of plain text files — and the data is not among them (yours lives in Databricks; the local cache is gitignored).1 Which means:

Power BI Desktop, the deploy pipeline, and Claude's agents are all just editors of the same text files. When the agent "adds a measure," it types DAX into a .tmdl file — the identical result to you clicking New measure in Desktop. There is no separate "agent format." If you can read the files, you can read the agent.

2 Three things at the top

Here is your EMEA Performance Dashboard, trimmed:1

EMEA Performance Dashboard.pbip            ← tiny pointer; "open me" in Desktop
EMEA Performance Dashboard.SemanticModel\  ← THE MODEL (tables, M, DAX, relationships)
EMEA Performance Dashboard.Report\         ← THE REPORT (pages, visuals, theme)

That split is the format. Power BI has always been two products in a trench coat — a tabular model engine and a visual canvas — and PBIP finally stores them as two folders. Everything you'll ever review sorts into one side or the other:

── the model side: TMDL ──────────────────────────────
EMEA….SemanticModel\definition\model.tmdl           model props, table ordering
EMEA….SemanticModel\definition\relationships.tmdl   every relationship
EMEA….SemanticModel\definition\tables\Date.tmdl     one file per table…
EMEA….SemanticModel\definition\tables\Measures - Base.tmdl  …incl. measure tables

── the report side: PBIR ─────────────────────────────
EMEA….Report\definition\report.json                 report-level filters/settings
EMEA….Report\definition\pages\Overview\page.json    one folder per page
EMEA….Report\definition\pages\Overview\visuals\kpiRevenue\visual.json
                                                    one folder per visual
EMEA….Report\StaticResources\RegisteredResources\LTDBrand.json  your theme
PBIX → PBIP translation

Model view, the fields pane, Power Query → *.SemanticModel. The canvas, format pane, bookmarks, themes → *.Report. The data you used to "keep in the file" → not in git at all (.pbi\cache.abf, gitignored).

3 The model side reads like YAML — TMDL

From your real tables\Measures - Base.tmdl:4

table 'Measures - Base'
    lineageTag: d9320412-0a28-4329-944c-56b9dd050c07

    measure Sales = SUM(gold_netsuite_daily_sales[sales_local])
        lineageTag: b8e2a2cc-…

        formatStringDefinition = SWITCH(SELECTEDVALUE('Market'[Currency]), "GBP", "£#,0;…")

    measure Units = SUM(gold_netsuite_daily_sales[sales_units])
        formatString: #,0
        lineageTag: 5374f870-…

    measure 'Stage Mix %' = DIVIDE([Sales], CALCULATE([Sales], REMOVEFILTERS('Stage'), …))
        formatString: 0.0%;-0.0%;0.0%

Five rules cover ~95% of reading TMDL:4

  • Nesting = ownership. Indented under table X ⇒ belongs to table X. There's no "measures:" list syntax — children just sit inside their parent. (On disk the indent is a tab; never "fix" the whitespace.)
  • = means expression. Whatever follows is DAX (or M), verbatim — exactly what you'd type in the formula bar. Multi-line expressions continue on the following lines, one indent deeper.
  • : means plain property. formatString: #,0, isHidden (bare = true), sortByColumn: 'Category Order'.
  • Names with spaces get single quotes — 'Stage Mix %' — same rule as DAX table references.
  • lineageTag is identity plumbing. Skip it when reading; expect one on anything new.
Review payoff

A TMDL diff is a DAX/M code review. measure Sales = … changed? Read the DAX. partition source = changed? The data feed changed — that's the highest-stakes edit a model PR can contain (and needs a refresh to take effect).

4 The report side is JSON, one file per visual — PBIR

Every page is a folder; every visual is a folder holding one visual.json. Your revenue KPI card, trimmed:5

{
  "$schema": "https://developer.microsoft.com/json-schemas/…/visualContainer/2.11.0/schema.json",
  "name": "kpiRevenue",
  "position": { "x": 16, "y": 163, "height": 106, "width": 300.8 },   ← WHERE
  "visual": {
    "visualType": "card",                                             ← WHAT
    "query": { "queryState": { "Values": { "projections": [ {
      "field": { "Measure": { "Expression": { "SourceRef": { "Entity": "Measures - Base" } },
                              "Property": "Sales" } }                 ← BOUND TO
    } ] } } },
    "objects": { "labels": [ { "properties": { "fontSize": { "expr": {
      "Literal": { "Value": "17D" } } } } } ] }                       ← STYLED HOW
  }
}

Read every visual.json with the same four questions: where (position), what (visualType), bound to what (query — note it names the model objects: entity Measures - Base, property Sales), styled how (objects — overrides on top of the theme). Visual-level filters ride along in filterConfig.

Two niceties: every file's $schema gives you IntelliSense + validation in VS Code5; and folder names like kpiRevenue are friendly renames (Desktop's default is a 20-char hex id) — your agents name them so PRs read like English.3

5 Thick vs thin — one line decides

Open definition.pbir and look at datasetReference. Two real files from your repo:3

EMEA Performance Dashboard.Report\definition.pbir — THICK: model travels with report
"datasetReference": {
  "byPath": { "path": "../EMEA Performance Dashboard.SemanticModel" }
}

Weekly Sales Summary.Report\definition.pbir — THIN: points at a published shared model
"datasetReference": {
  "byConnection": { "connectionString": "…;initial catalog=\"Sales Reports\";…
                     semanticmodelid=f92eda3c-52bc-4ac9-b337-10bd4fbcd6ac" }
}

A thin report has no .SemanticModel folder at all. Ask an agent to "fix a measure" in Weekly Sales Summary and the edit must land in the shared Sales Reports model project — where it affects every other thin report on that model. This is the single most common routing mistake to catch in review.

6 Payload vs plumbing

Not every changed file deserves your attention. The full triage table is the File Map reference — the short version:

  • read — tables\*.tmdl, relationships.tmdl, visual.json, page.json, report.json, definition.pbir, theme, .platform (display names are load-bearing for deploys).
  • glance — model.tmdl (ref reordering ≈ churn; a new ref = new object), definition.pbism, pages.json, version.json.
  • noise — lineageTag lines, cultures\*.tmdl, diagramLayout.json, mobileState.json. And .pbi\ files should never appear in a PR at all.

7 So what is the agent doing in there?

Mapping your installed tooling onto the two layers demystifies most tool calls you see scroll past:

When the agent…It's usingFiles touched
edits measures/columns/partitions as text pbip:tmdl · semantic-models:* *.SemanticModel\definition\*.tmdl
works the live model in a running Desktop powerbi-modeling MCP · connect-pbid none directly — TOM edits, serialized to TMDL later
creates/moves/styles visuals & pages reports:pbir-cli · pbip:pbir-format *.Report\definition\pages\**
scaffolds a new LTD-branded report new-report (repo skill) whole project incl. LTDBrand.json
checks structure before a PR deploy/validate.py · pbip:pbip-validator reads everything, writes nothing
merges to main fabric-cicd (deploy/) → production workspaces

8 Practice — make it stick

Retrieval beats re-reading. Answer from memory; feedback is instant.

Exercise A · Retrieval

Which side of the trench coat? Tag each file.

SemanticModel = the model item. Report = the visual layer.

Exercise B · PR triage

An agent PR changes five files. Click the one that means DAX logic changed.

Think: which layer owns measures?

EMEA….Report\definition\pages\Overview\visuals\kpiRevenue\visual.json EMEA….Report\StaticResources\RegisteredResources\LTDBrand.json EMEA….SemanticModel\definition\tables\Measures - Base.tmdl EMEA….Report\definition\pages\pages.json EMEA….SemanticModel\.platform
Exercise C · Predict, then reveal

You ask the agent: "fix the Sales measure that Weekly Sales Summary shows wrong." Where should the PR's edit land?

The shared Sales Reports model. Weekly Sales Summary is a thin report — its definition.pbir is byConnection (semanticmodelid=f92eda3c…), so option A's folder does not exist. The measure lives in the shared model's project, and fixing it there changes every report bound to that model — which is exactly why this edit deserves review.

Nuance: a report-scoped measure could live in the thin report's reportExtensions.json — the one legitimate place DAX hides inside a report. Shared logic still belongs upstream in the model.
