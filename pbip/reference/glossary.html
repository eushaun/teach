Glossary

The canonical vocabulary for this course. Lessons link here; meanings stay consistent across every lesson. Forward-referenced terms are marked soon.

PBIP (Power BI Project)
A report + semantic model saved as a folder of plain-text files instead of a single binary. The <name>.pbip file itself is just a tiny JSON pointer to the report folder; the substance lives in the *.SemanticModel and *.Report folders next to it. Review cue: "the PBIP" = the whole folder tree, and it is exactly what lives under powerbi-pbip/reports/<Workspace>/<Project>/.
PBIX
The classic single-file format: a zip archive containing the same report + model metadata (in older, undocumented encodings) plus the imported data cache. Fine for Desktop, opaque to git — you can't diff or merge it. Everything you built in PBIX still exists in PBIP — it's the same objects, spelled out in text.
Semantic model (*.SemanticModel folder)
The "dataset": tables, columns, partitions (with their M), relationships, measures, roles, cultures. In our projects it's serialized as TMDL under definition\. Model view + the fields pane, as files.
Report (*.Report folder)
The visual layer: pages, visuals, bookmarks, themes, report/page/visual-level filters and formatting. Serialized as PBIR JSON under definition\. The report canvas, as files — one folder per page, one per visual.
TMDL (Tabular Model Definition Language)
Indentation-based text language for tabular models. Objects declare children by nesting (a measure under a table); = introduces an expression (DAX/M, read verbatim), : introduces a plain property (formatString: #,0). On disk: tab-indented, one file per table. Review cue: the DAX after = is exactly what you'd type in Desktop's formula bar — nothing is re-encoded.
TMSL / model.bim
The older JSON serialization of the same tabular model, stored as one giant model.bim file. A project uses TMDL or TMSL, never both. You'll only meet it in legacy exports; our repo is all-TMDL.
PBIR (Power BI Enhanced Report format)
The source-control-friendly report format: properly formatted JSON, one file per page/visual/bookmark, each with a public $schema. Designed for diffs, merges, and programmatic edits. Every report in our repo is PBIR — it's what makes agent edits reviewable at all.
PBIR-Legacy (report.json)
The predecessor: the whole report crammed into a single undocumented report.json. Doesn't support external editing. If you ever see one report.json instead of a definition\ folder, the report hasn't been converted to PBIR.
definition.pbir
The report folder's core file. Its datasetReference says which model the report runs on: byPath (relative path to a local *.SemanticModel) or byConnection (connection string to a published model in the Service). This one file decides thick vs thin — and rebinding a report = editing it.
definition.pbism
The semantic model folder's core file: format version + core settings. Version 4.0+ permits TMDL; the file is otherwise boring. Don't confuse the pair: .pbir = report, .pbism = semantic model.
Thick report (byPath)
Report + its own model in one project; definition.pbir points byPath at the sibling *.SemanticModel. Opening it in Desktop opens both for editing. Our specimen: EMEA Performance Dashboard. A PR here can legitimately touch both folders.
Thin report (byConnection)
Report only; definition.pbir carries a connection string (semanticmodelid=…) to a shared model published in the Service. There is no local model folder. Our specimen: Weekly Sales Summary → the shared Sales Reports model. A "measure fix" PR for a thin report must land in the shared model's project instead.
.platform / logicalId
Fabric's git-integration identity file: item type, display name, and a logicalId GUID that ties the folder to a Service item. One per *.Report and *.SemanticModel. Duplicate logicalIds (e.g. a stray .bak copy) hard-fail deploys; display names are load-bearing for fabric-cicd matching. Diffs here are rare and worth a close look.
lineageTag
A stable GUID stamped on model objects (tables, columns, measures) so tooling can track identity across renames and deployments. Pure noise when reading a diff — but additions should come with one, and they must stay unique.
visual.json
One visual, one file: its name, position (x/y/z, width/height), visualType, query (which fields/measures it projects) and objects (formatting overrides). The three questions of any visual diff: moved? re-bound? re-styled? — map to exactly those three blocks.
page.json / pages.json
page.json (one per page folder) holds page size, page-level filters and formatting; pages.json (one per report) holds page order + active page. A visual "disappearing" in a PR is as likely a pages.json ordering / page.json filter change as a deleted visual folder.
reportExtensions.json soon
Report-scoped extensions — most notably report-level measures that live in the report, not the model. The one legitimate way DAX can hide inside a thin report's PR.
StaticResources / RegisteredResources
Report-local resource files: the applied theme JSON (ours: LTDBrand.json), base themes, images. Brand-wide look changes should land here (or in the _template), not as per-visual objects overrides.
Partition (model) soon
The part of a table's TMDL that says where its data comes from — for us an M (Power Query) expression querying Databricks dwh, declared as partition X = m with the M after source =. A partition diff = "the data feeding this table changed" — highest review priority in any model PR.
ref (TMDL keyword)
Ordering declarations in model.tmdl (ref table Sales…) that preserve collection order across serialization round-trips. A reshuffled ref block is usually serializer churn, not a semantic change — but a new ref means a new table/culture/role exists.
TOM (Tabular Object Model) soon
The .NET client API for tabular models. The live-model route: the powerbi-modeling MCP and connect-pbid talk TOM to a running Desktop's local Analysis Services instance instead of editing files. Two routes, one truth: live TOM edits and on-disk TMDL edits must not fight — never let Desktop save over hand-authored TMDL.
.pbi\ / cache.abf / localSettings.json
Machine-local plumbing: cache.abf is the imported data cache, localSettings.json per-machine settings. Gitignored by the default PBIP .gitignore. If these show up in a diff, something's wrong with the .gitignore — they never belong in a PR.
fabric-cicd soon
Microsoft's Python library that publishes PBIP folders to a Fabric/Power BI workspace — the engine inside our deploy/ tooling. Matches items by display name + type. Why "merging to main IS the prod deploy," and why renames create duplicates instead of renaming.
