Arrays, Objects, and the Shape of Your Data

Lists and records — and the moment TypeScript starts paying off for a data engineer: the compiler catches a misspelled field name that Python would have shipped to production.

Mission link: nearly everything an MCP server does is "receive a shaped record, do something, return a shaped record." Today you learn to describe those shapes. This is the on-ramp to reading real SDK code.

1 · Arrays — your lists

PythonTypeScript
tables: list[str] = [
    "fact_orders",
    "dim_customers",
]
tables.append("dim_products")
n = len(tables)
first = tables[0]
 
const tables: string[] = [
  "fact_orders",
  "dim_customers",
];
tables.push("dim_products");
const n = tables.length;
const first = tables[0];

The type is string[] — element type, then square brackets. Works for any type: number[], boolean[]. (You'll also see the equivalent Array<number> in the wild.) Inference works here too: const xs = [1, 2, 3] is already number[] without an annotation. Source: Everyday Types.

Two Python habits that bite here:
  • Don't write [string] — that means something different (a tuple of exactly one string), not an array.
  • No negative indexing. tables[-1] quietly gives you undefined, not the last element. Use tables.at(-1) or tables[tables.length - 1].

And a const subtlety worth noticing in the example above: tables.push(...) is legal on a const array. const means the name can't be re-pointed at a different array — the array's contents can still change. (Same spirit as a Python tuple holding a list.)

Looping: for...of

PythonTypeScript
for t in tables:
    print(t)
 
for (const t of tables) {
  console.log(t);
}
The of/in trap: TypeScript also has for...in, and your Python muscle memory will reach for it — but it iterates indices ("0", "1", "2"), not values. For values, it's always of.

2 · Objects — they look like dicts, they behave like TypedDicts

Here's a record in both languages:

PythonTypeScript
sync = {
    "table": "fact_orders",
    "rows_loaded": 120_000,
}
print(sync["table"])
 
const sync = {
  table: "fact_orders",
  rowsLoaded: 120_000,
};
console.log(sync.table);
The mental model: a TypeScript object literal looks like a Python dict, but treat it like a TypedDict or dataclass instance: fixed, known fields with individual types, accessed with dot notation, and typo-checked by the compiler. sync.tabel is a compile error, not a 2am KeyError.

Note the differences: keys are unquoted, and access is sync.table, not sync["table"]. If you're thinking "but sometimes I need a real dict — arbitrary keys discovered at runtime" — you're right, and TypeScript has containers for that (Record, Map). Parked for a later lesson; today is about records with known shapes.

3 · Type aliases — naming a shape

Inline object types get unwieldy fast. A type alias gives the shape a reusable name — Python's class TableSync(TypedDict), in one line:

type TableSync = {
  table: string;
  rowsLoaded: number;
  success: boolean;
  errorMessage?: string;   // ? = optional, like NotRequired[str]
};

Now TableSync works anywhere a type works — parameters, returns, and arrays of records:

function describeSync(sync: TableSync): string {
  return `${sync.table}: ${sync.rowsLoaded} rows`;
}

const results: TableSync[] = [ /* ... */ ];   // a typed result set

Three details worth knowing, straight from the handbook:

  • Inside a type definition, separate members with ; (convention) — commas are also legal. Inside an object literal (the data), it's always commas.
  • errorMessage? means the field may be absent. A record without it is fine; a record missing success is a compile error.
  • You'll also meet interface in the wild — it does the same job for object shapes. We'll compare them later; read it as "same idea" for now.

4 · Hands on — a typed pipeline report

Open the Playground, clear it, and paste:

type TableSync = {
  table: string;
  rowsLoaded: number;
  success: boolean;
  errorMessage?: string;
};

const results: TableSync[] = [
  { table: "fact_orders", rowsLoaded: 120_000, success: true },
  { table: "dim_customers", rowsLoaded: 8_500, success: true },
  { table: "dim_products", rowsLoaded: 0, success: false, errorMessage: "API rate limit hit" },
];

for (const sync of results) {
  console.log(`${sync.table}: ${sync.rowsLoaded} rows`);
}
1

Run it. Three lines in the Logs — you just looped over a typed result set. Notice the third record has errorMessage and the others don't: that's the ? doing its job.

2

The typo test. Change sync.table to sync.tabel. Instant squiggle: "Property 'tabel' does not exist on type 'TableSync'." In Python, sync["tabel"] passes every linter and explodes at runtime — in whichever environment first hits that code path. Here it cannot compile. Fix it back.

3

The missing-field test. Delete success: true, from the first record. Read the error — the compiler tells you exactly which required property is missing from which record. Restore it.

4

Write totalRows from scratch. A function taking TableSync[] and returning the total of all rowsLoaded as a number. You'll need an accumulator — your first legitimate use of let (and += works exactly like Python). Verify:

console.log(totalRows(results));  // should print: 128500

While typing, pause after sync. and watch the autocomplete — the editor knows every field. That's the shape information working for you.

5

A teaser for next time. Hover over errorMessage in results[2].errorMessage (add that line if you like). The tooltip says string | undefined — "string or undefined." That vertical bar is a union type, and it's how TypeScript forces you to handle the maybe-missing case before using the value. That story — unions, null/undefined, and narrowing — is coming soon.

Your win today: you modelled a pipeline result set as typed records, and the compiler caught both a misspelled field and a missing field — the two classic dict bugs Python only reveals at runtime.
