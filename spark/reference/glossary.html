Glossary

The canonical vocabulary for this course. Lessons link here; meanings stay consistent across every lesson. Forward-referenced terms are marked soon.

Driver
The single process that runs your program, builds the execution plan, and schedules work onto the cluster. It does not process the bulk of the data — it coordinates. Debugging cue: collect() pulls data to the driver; too much → driver OOM.
Executor
A JVM process on a worker node that actually runs tasks and holds data partitions in memory/disk. A cluster has many; each has a fixed number of cores and a memory budget. Tuning cue: total parallelism ≈ (executors × cores).
Partition
A contiguous chunk of a distributed dataset — the unit of data. One partition is processed by one task at a time. Too few = under-parallelised; too many tiny ones = scheduling overhead. This balance recurs in almost every tuning decision.
Transformation
An operation that defines a new dataset from an existing one (select, filter, join, groupBy, withColumn). It is lazy — it builds the plan but runs nothing.
Action
An operation that asks for a result and therefore triggers execution (count, collect, show, write, take). One action ≈ one job.
Lazy evaluation
Spark records transformations without running them, building up a plan, until an action forces execution. This is why optimization is possible: Spark sees the whole chain at once and can rewrite it (push filters down, prune columns) before running.
Job
The unit of work triggered by one action. A job is split into stages.
Stage
A set of tasks that can run together without moving data across the network. Stage boundaries occur at shuffles. A job has as many stages as it has shuffles, plus one.
Task
The smallest unit of execution: one task processes one partition of data within a stage. Tasks of a stage run in parallel across executor cores.
Shuffle
The physical redistribution of data across partitions (and usually across the network) so that rows sharing a key land together — required by groupBy, join, distinct, repartition. The most expensive thing Spark does (disk + network + serialization). Every stage boundary is a shuffle. Reducing/avoiding shuffles is the #1 perf lever.
Narrow transformation
Each input partition contributes to exactly one output partition (filter, select, map). No shuffle; stays within a stage; runs pipelined.
Wide transformation
Input partitions feed many output partitions, requiring a shuffle (groupBy, join, distinct). Causes a stage boundary.
DAG (Directed Acyclic Graph)
The graph of transformations Spark builds for a job. The DAGScheduler splits it into stages. You see it visualised in the Spark UI.
Catalyst soon
Spark SQL's query optimizer. It turns your DataFrame/SQL code into an optimized physical plan through a pipeline of rules (analysis → logical optimization → physical planning). Covered in Lesson 3.
Query plan soon
The tree of operators Spark will execute, viewable with df.explain(). Stages: unresolved → analyzed → optimized logical → physical. Lesson 3.
AQE (Adaptive Query Execution) soon
Runtime re-optimization: at each shuffle boundary Spark uses actual statistics to coalesce partitions, switch join strategies, and handle skew. On by default in Spark 3.2+ and on Databricks. Covered later.
Slot / core
An execution slot on an executor (≈ one CPU core). A slot runs one task at a time, so total concurrent tasks ≈ total slots. This caps real parallelism regardless of partition count.
Window function
Computes a value for every row using that row's partition-mates — defined by partitionBy (which rows belong together), orderBy (their sequence), and a frame (which of them feed this row's value). Unlike groupBy, rows are not collapsed. Engine cue: partitionBy keys are shuffle keys — a window spec is a shuffle wearing analytics clothing. Specs with identical keys can share one exchange.
Window frame
The slice of the (ordered) partition that feeds the current row's value — e.g. rowsBetween(unboundedPreceding, currentRow) for a running total. Defaults when omitted: no orderBy → the whole partition; with orderBy → a growing RANGE frame up to the current row, ties included as peers. Silent-bug source: the RANGE default pulls in all order-by ties at once. State frames explicitly (rowsBetween) — say the frame you mean.
Exchange
The physical operator that implements a shuffle — what df.explain() and the Spark UI's SQL DAG show as Exchange hashpartitioning(keys, n). Several downstream operators needing the same row distribution (e.g. two window specs with identical partition keys) can be fed by a single exchange. Counting exchanges in a plan = counting shuffles = counting stage boundaries. Plan reading is Lesson 3.
Cache / persist
df.cache() marks a DataFrame so its computed partitions are kept (memory, spilling to disk) the first time an action materializes them; later actions reuse the stored partitions instead of replaying the whole lazy recipe. Itself lazy — a marker, not an action. Release with unpersist(). The cheapest fix for "one expensive lineage, many actions" — compute once, then assert + check + write against the cached result.
