2 FIFO without a loop: the number line

Said aloud, FIFO aging is a loop: "take the oldest receipt, subtract what's shipped, carry the remainder, move to the next…". Loops over rows don't distribute. Your pipeline never writes that loop — it restates the problem as set math the cluster can run on every (item, location, snapshot) at once.

Put each item-location's inflows on a number line of cumulative units, oldest first. A layer received as quantity units occupies the interval (cum_start, cum_end], where cum_end is the running sum of inflows up to and including it, and cum_start = cum_end − quantity. Because layers sit on the line in receipt order, FIFO consumption — whenever each shipment actually happened — always eats the line from unit 1 rightward. So by any snapshot date, only one number matters: total_outflow, how far the eating has reached.

total_outflow = 60 units, eaten from the left
Jan · 40 Mar · 30 May · 50
(0, 40] (40, 70] (70, 120]
Layer state: consumed · partial (survives 70−60 = 10) · untouched

A layer survives wherever the eating hasn't reached — the part of its interval to the right of total_outflow:

cum_start     = cum_end - quantity
surviving_qty = greatest(                                  # clamp at 0
                  least(quantity,                          # clamp at full layer
                        cum_end - greatest(total_outflow, cum_start)),
                  lit(0.0))

Three cases, one expression.
Untouched — total_outflow ≤ cum_start → survives quantity.
Fully consumed — total_outflow ≥ cum_end → survives 0.
Partial — in between → survives cum_end − total_outflow.
No branching, no loop — the greatest/least clamps carve all three cases out of the same subtraction.

Algebra as QA

Summed over all layers of an (item, location): Σ surviving_qty = total inflow − total outflow = the net ledger sum. That identity is not a vibe check — it's a theorem about the formula. Your pipeline runs it as a hard assert on every run. When you derive results with set math, invariants like this come free; use them.

Exercise A · Walk the number line

Three layers: 100, then 50, then 80 units (oldest → newest).

L1 · 100 L2 · 50 L3 · 80
(0, 100] (100, 150] (150, 230]

Suppose total_outflow = 120. Predict before you click.

A1. How many units of L1 survive?

0. L1 spans (0, 100] and the eating reached 120 — past its cum_end. total_outflow ≥ cum_end → fully consumed.

A2. How many units of L2 survive?

30. L2 spans (100, 150]; the eating reached 120, inside the interval. Partial case: cum_end − total_outflow = 150 − 120 = 30.

A3. Total surviving across all three layers — without touching L3?

110 — by the identity. Total inflow 230 − total outflow 120 = 110. (Check: 0 + 30 + 80 = 110; L3 at (150, 230] is untouched.) This shortcut is your pipeline's hard assert.

3 Two window specs, one shuffle

The formula needs two aggregates per row: a running inflow total (cum_end) and a whole-partition outflow total (total_outflow). Your pipeline builds them from two window specs:

w_partition = Window.partitionBy("item_id", "location_id", "as_of_date")

w_cum = (
    w_partition
    .orderBy("trandate", "transaction_id", "transactionline_id")
    .rowsBetween(Window.unboundedPreceding, Window.currentRow)
)

df = (
    df.withColumn("cum_end",
        sum(when(col("quantity") > 0, col("quantity")).otherwise(lit(0.0))).over(w_cum))
      .withColumn("total_outflow",
        sum(when(col("quantity") < 0, abs(col("quantity"))).otherwise(lit(0.0))).over(w_partition))
)

A window function computes a value for every row from that row's partition-mates.3 To do that, the engine must physically bring each partition's rows to one place — and "move rows so that keys meet" is exactly Lesson 1's shuffle. partitionBy is the shuffle. In the physical plan it appears as an exchange: Exchange hashpartitioning(item_id, location_id, as_of_date).

The two specs then diverge on what happens after the rows land:

  • w_cum — ordered, explicit frame. orderBy adds a sort-within-partition requirement, and rowsBetween(unboundedPreceding, currentRow) makes the frame grow row by row — a running total. Receipt order is what makes cum_end mean "units up to and including this layer".
  • w_partition — no ordering, no frame. The documented default: "when ordering is not defined, an unbounded window frame … is used"2 — i.e. the whole partition. Result: one total, repeated on every row. That's total_outflow.
The frame default that bites

The other default matters more: with orderBy but no frame, Spark uses a growing RANGE frame2 — and RANGE treats order-by ties as peers, including them all at once. Here the ordering key is the row's PK (unique), so RANGE would coincidentally match — but on a tied key (just trandate, say) a running sum silently jumps by whole groups. Your pipeline's explicit rowsBetween is the tie-proof habit: say the frame you mean.

Now the engine-lens punchline. Both specs name identical partition keys, so one exchange satisfies both: the planner hash-partitions once, sorts once (only w_cum asked for order), and stacks the two Window operators on top.4 Expect this shape in the SQL DAG:

Exchange hashpartitioning(item_id, location_id, as_of_date, 200)
  Sort (trandate, transaction_id, transactionline_id)      ← only w_cum needs this
    Window [sum(...) over w_cum]                            ← running: cum_end
    Window [sum(...) over w_partition]                      ← whole-partition: total_outflow

The match must be exact. A spec on (item_id, location_id) alone would not reuse this exchange — hashing on three keys doesn't co-locate rows by two — and you'd pay a second shuffle. One more reading detail: total_outflow is computed while the outflow rows are still in the DataFrame; only afterwards does .where(quantity > 0) keep the inflow rows as layers. Filter first and the outflows would vanish from the sum — order of transformations is part of the algorithm.

4 The ×23 that costs almost nothing

Before the windows, the pipeline does something that sounds alarming:

df = df_ledger.crossJoin(df_as_of).where(col("trandate") <= col("as_of_date"))

A cross join! But look at the sizes. The as-of dimension is 23 rows. Spark handles a join with a tiny side by broadcasting it — shipping the 23 rows to every executor once, then expanding each ledger row locally (a BroadcastNestedLoopJoin).6 No rows are redistributed, so: no shuffle, no stage boundary. The scary word and the expensive operation are not the same thing.

The real cost is row multiplication: ~340k × 23 ≈ 8M rows (the trandate ≤ as_of_date filter then trims older snapshots' futures away). That inflated set is what flows into the window exchange — and it's a price paid on purpose: putting as_of_date into the partition keys is what makes all 23 snapshots' FIFO walks independent, so the cluster computes two years of month-ends in one pass instead of 23 job runs.

Small print from Lesson 1

Building that dimension does UNION … .distinct() — and distinct is a wide transformation, so yes, there's technically a shuffle there… of 23 rows. Shuffle size is the cost, not the word "shuffle". Reserve your alarm for exchanges moving millions of rows.

5 One cache, four actions

The build cell ends with:

df_gold = compute_fifo_layers(df_ledger, df_as_of, AGING_THRESHOLD_MONTHS).cache()

Then four separate cells consume df_gold: the identity assert (.count()), the soft QOH comparison (display()), the PK-uniqueness assert (.count()), and the gold write (saveAsTable). Lesson 1's lazy evaluation has a sharp edge here: a DataFrame is a recipe, not a result. Without cache, each of those four actions would replay the entire lineage — three-table join, broadcast expansion, the shuffle, the sort, both windows — from the silver tables.

With .cache(), the first action materializes the partitions (memory, spilling to disk if needed5) and the other three read them back. Remember the warm-up: cache() itself is lazy — a marker, not an action. And the pipeline's last line, df_gold.unpersist(), hands the memory back when the work is done. Marker on, work, marker off: the cheapest real tuning lever in this file.

6 What you can now predict

Next time the netsuite2 job runs this task, you can call the plan before opening it:

  • No panic at crossJoin: a 23-row side means broadcast — no exchange, no stage boundary.
  • One exchange for both windows: hashpartitioning(item_id, location_id, as_of_date), one sort (owned by w_cum), two Window operators. If you ever see two exchanges stacked here, a spec's keys drifted.
  • Four actions, one computation: .cache() is why the three checks are near-free instead of tripling the runtime.
