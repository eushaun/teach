Lesson 1 · Spark Engine

The Execution Model

What actually happens between your df code and work running on the cluster — the map every later lesson hangs on.

Why this lesson (your mission)

You want to tune for cost/performance, debug failures, and design pipelines well. All three start in the same place: a clear picture of how the engine turns your code into jobs, stages, and tasks. Get this and the Spark UI stops being noise — it becomes a map of exactly these things.

Your win for today: take any PySpark snippet and predict (a) which line actually triggers work, and (b) where the engine splits that work into stages. That single skill is the foundation of reading query plans (Lesson 2) and the Spark UI (Lesson 4).

1 Two kinds of machine

A Spark cluster is one driver and many executors.2 The driver runs your program and decides what to do; the executors do the heavy lifting in parallel.

Driver · 1
Runs your code. Builds the plan. Schedules & tracks tasks. Collects results.
Does not crunch the data.
Executor
JVM on a worker. Holds partitions; runs tasks on its cores.
Executor
…many of these. Real parallelism ≈ executors × cores.
Debugging payoff

collect() and toPandas() pull all data back to the single driver. The classic "my driver OOM'd" is usually this. Knowing the driver/executor split tells you instantly where to look.

2 Nothing runs until you ask for a result

Spark operations come in two flavours:3

  • Transformations (filter, select, join, groupBy, withColumn) describe a new dataset. They are lazy — they build a recipe and run nothing.
  • Actions (count, collect, show, write) ask for a result, and that is what triggers execution.
df = (spark.read.parquet("/sales")   # nothing runs
        .filter(col("country") == "UK")   # nothing runs
        .withColumn("net", col("amt") * 0.8))  # nothing runs

df.count()   # ← an ACTION: NOW the engine runs everything above

Why lazy? Because Spark waits, it sees your entire chain before running a thing. That's what lets the optimizer rewrite it — e.g. push the filter down to the file read so it never loads UK-irrelevant rows. Eager execution couldn't do that. Laziness is the feature that makes optimization possible.1

3 Action → Job → Stages → Tasks

When an action fires, the engine builds a four-level hierarchy.2 Memorise this ladder — it is the Spark UI:

Job — one action triggers one job.
Stage — a job is cut into stages at every shuffle. (Stages = shuffles + 1.)
Task — within a stage, one task runs per partition, in parallel across cores.

The only thing that creates a stage boundary is a shuffle: moving data across the network so rows with the same key meet. Operations that need this — groupBy, join, distinct, repartition — are wide. Operations that don't — filter, select, withColumn — are narrow and stay inside one stage.

The whole game, in one sentence

Narrow transformations are cheap and pipeline together; shuffles are expensive and cut your job into stages. Counting and shrinking shuffles is the heart of Spark performance tuning.

Exercise C · Predict, then reveal

How many shuffles (stage boundaries) does this job have?

(customers.join(orders, "customer_id")   # combine two tables
          .groupBy("region").count()      # count per region
          .show())                         # action
Two shuffles. The join redistributes both tables by customer_id so matching rows meet (shuffle 1). The groupBy("region") then redistributes again by region (shuffle 2). show() is the action that triggers it all.

Nuance for later: the exact stage count also depends on the join strategy — if orders were tiny, Spark could broadcast it and skip the join's shuffle entirely. That's AQE & join strategy, coming in a later lesson.

5 Where this takes you

You now have the skeleton the rest of the course hangs on:

  • Debugging: the Spark UI's Jobs → Stages → Tasks tabs are literally this ladder. A slow job = find the slow stage; a slow stage = find the straggler task (often skew).4
  • Performance: "make it faster" almost always means "remove or shrink a shuffle," because shuffles are the stage boundaries you just learned to spot.
  • Architecture: choosing partitioning & join strategy is choosing how many shuffles your pipeline pays for.
