Lesson 1 · Warehouse Forecast App

The Map: Four Layers, One Primitive

Where everything in Matt's app lives, and the one idea that produces every number a planner sees.

Why this lesson (your mission)

As maintainer, every question you get ("the sync failed", "this cover looks wrong", "AU is blank", "the deploy broke it") lands in exactly one layer of this app. This lesson gives you the map, so your first move is always the right file. Every path and line below was checked against your local checkout (main @ 135eac9; production runs origin/main, two commits ahead).

Your win for today: place any symptom or file in one of four layers, and know that every number on every page is a reading of one projection.

1 Four layers, and Infra around them

 Databricks dwh.*                                     ← your side; the app only reads it
     │  18 steps, daily 12:00 UTC + "Sync Now"
 ① SYNC          databricks_sync.py, run by APScheduler inside the web process
     ▼
 ② STORAGE       Postgres 16 on the same box: 30 tables (mirrors · rollups · app state)
     ▲
 ③ API + ENGINE  FastAPI: routers → services (the engines) → response cache
     │  JSON over /api/*, behind Caddy (TLS) on one EC2 box
 ④ UI            React 19 SPA in the planner's browser
 ─────────────────────────────────────────────────────────────
 INFRA           push to main → Bitbucket Pipelines → ECR → SSM → EC2

① Sync. One file, backend/app/services/databricks_sync.py, pulls from your dwh tables into Postgres. The trigger is not a Databricks job or a cron on the host. An APScheduler job is registered inside the FastAPI process itself (main.py:37).19 The orchestrator run_incremental_sync (databricks_sync.py:1703) calls each step in order.2

② Storage. Postgres tables defined by SQLAlchemy models in backend/app/models/ and created by Alembic migrations in backend/alembic/versions/, which run on every container start. Three kinds of table: raw mirrors of dwh (daily_sales, inventory_levels…), rollups the sync rebuilds (monthly_warehouse_velocity), and app state planners edit (fba_replenishment_config, alert_thresholds, users).

③ API + Engine. backend/app/main.py mounts four routers (:81-84): auth, dashboard, sync, admin.1 This is FastAPI's standard APIRouter "bigger applications" layout.8 Handlers in routers/ call plain-function modules in services/, which is where every engine lives. Results are shaped by Pydantic models in schemas/ and held in an in-process response cache.

④ UI. frontend/src/App.tsx declares the routes (:115 onward), one per page component in frontend/src/pages/. Each page fetches its data through typed functions in frontend/src/api/. In production the same FastAPI process serves the built React files.

Python bridge

The backend half will feel familiar: it has the same shape as your MCP servers (FastAPI routers, Pydantic models, a settings class). The new parts are the domain in services/ and the React half, which we'll take just-in-time from L7.

2 The one primitive

Until September 2026 the app had six separate projection loops, each with its own horizon and its own idea of demand, and their numbers sat side by side "as though they agree".6 Matt's projection alignment programme replaced them with one module. Its docstring opens: "Every cover figure, order quantity and urgency band in the app is a reading of the same thing."3

The recipe: opening stock → projection.project(...) over periods from a DemandSeries, with arrivals from inbound grading → take a reading. Policy goes in the inputs, never in a forked loop.

The whole loop, from backend/app/services/projection.py:279-289:3

    points: list[ProjectionPoint] = []
    running = float(opening_soh)
    for i, p in enumerate(periods):
        items = by_period.get(i, [])
        arrived = sum(a.quantity for a in items)
        demand = p.demand
        closing = running + arrived - demand          ← nothing is floored
        points.append(ProjectionPoint(p, running, arrived, demand, closing, items))
        running = closing

    return Projection(float(opening_soh), points, dropped)

That's a running balance, nothing more. The engines differ only in what they feed it and which question they ask of the result. There are four readings: weeks_of_cover, min_point, deficit_against and gap_before (projection.py:188-226). Cover pages ask the first. Quantity pages (Transfers, Replenishment) ask deficit_against. Lesson 2 takes them one at a time.

The full engine picture, from the demand tables down to which pages use which reading, is section 2 of the Architecture Map.

3 Trace one number

A Dashboard row shows a small bar and a figure under Riverside, say 6.5 wk (synthetic). Here is where it comes from, top to bottom. This chain is the core skill of the course.

  1. UI frontend/src/pages/Dashboard.tsx:366-385 renders the bar from row.warehouse_totals[wh].weeks_of_cover. The bar's width is woc / 26, so it is full at 26 weeks even though the figure caps at 52. The data was loaded by a useEffect (:80-98) that calls fetchStockCover() (:85) and re-runs when the market changes.4
  2. UI frontend/src/api/dashboard.ts:28-33 issues GET /dashboard/stock-cover. The axios interceptor at api/client.ts:24-31 appends ?market=US from the zustand market store.4
  3. API main.py:82 mounts the dashboard router at /api/dashboard. routers/dashboard.py:94 stock_cover checks the cache (:105), reads opening stock with get_physical_soh (:113), and calls get_batch_seasonal_woc (:118). It then packs seasonal_woc[(wh_name, sku)] into a WarehouseCover (:168-173) and caches the response (:225).5
  4. Engine services/warehouse_velocity.py:310 get_batch_seasonal_woc builds demand with location_demand (:374) and arrivals with _batch_fetch_incoming (:376). For each pair it calls _cover_for (:391), which runs project(..., early_arrivals="credit") over 52 weekly periods (:431-435) and reads weeks_of_cover(cap=52) (:436).5
  5. Engine services/demand.py:713 location_demand asks demand_channels_for_location. Riverside (124) is the market's hub, so the answer is ALL_CHANNELS (:647-648). Its demand is every US sale, built by channel_demand(..., None, ...) (:758-761), which reads monthly history from daily_sales via velocity.get_batch_monthly_history (demand.py:589, velocity.py:62).5
  6. Engine Arrivals: _batch_fetch_incoming (warehouse_velocity.py:293-307) delegates to inbound_grading.graded_incoming_by_location (inbound_grading.py:382). That grades lots from amazon_fba_inbound (:281) and open_purchase_orders (:328) in grade_inbound (:242), then adds open transfer_orders (:437).5
  7. Storage Postgres daily_sales, unique on (date, country, channel, sku, revenue_type).
  8. Sync databricks_sync.py:135 sync_daily_sales selects from dwh.netsuite.gold_netsuite_daily_sales_by_customer (:168) and upserts ON CONFLICT (:253), re-pulling the last 7 days each night.2
  9. Source Your gold table in dwh.netsuite. Rename a column there and step 1 of the sync fails, which aborts the whole run.
What the trace tells a maintainer

A "wrong" Riverside cover has exactly three suspects: opening stock (inventory_levels), demand (daily_sales, all channels, because it's the hub), or arrivals (graded POs and TOs). Every other page's number has the same three suspects, fed through different inputs.

4 The maintainer's three rules

1 · No tests. The harness (tools/compare_projections.py) is the gate, and a push to main deploys to production.

2 · Every service defaults market="US". A call that forgets market=market breaks AU silently.

3 · The response cache has no TTL. Bump CALC_BASIS_VERSION with any rule change.

Exercise F · Re-draw the chain from memory

On paper, re-draw the trace from the Riverside cover bar down to dwh. Then check one hop: which Postgres table is Riverside's demand built from?

daily_sales. Riverside is the hub, so its basis is all-channel sales, not its own SOH depletion (that's Walmart's). The chain:
Dashboard.tsx bar → fetchStockCover → GET /api/dashboard/stock-cover (+ ?market) → routers/dashboard.py stock_cover → warehouse_velocity.get_batch_seasonal_woc → _cover_for → projection.project → weeks_of_cover(cap=52)
inputs: opening = get_physical_soh (inventory_levels) · demand = demand.location_demand → hub → channel_demand → daily_sales ← sync step daily_sales ← dwh.netsuite.gold_netsuite_daily_sales_by_customer · arrivals = inbound_grading ← open_purchase_orders / amazon_fba_inbound / transfer_orders.

Missed a hop? That's the one to rehearse before Lesson 2.
