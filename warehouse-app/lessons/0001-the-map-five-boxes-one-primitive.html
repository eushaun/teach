Lesson 1 · DreamCast (warehouse-forecast-app)

The Map: Five Boxes, One Primitive

How DreamCast is built, where it runs, how data moves through it, and how a change reaches production. Draw it once here; every later lesson zooms into one box.

Why this lesson (your mission)

As the likely maintainer, every question you get ("the sync failed", "this cover looks wrong", "a reader can't open Transfers", "the deploy broke it") lands in one box of this system. Knowing which box is your first move every time. Every path and line below was checked against origin/main @ 380ff8f (v2.26, 13 Nov 2026), the commit production runs. This lesson replaces the October lesson 1, which was written before 57 commits changed most of the picture; assume none of it.

Your win for today: draw DreamCast from memory (five boxes, Infra around them, one primitive in the middle) and, given a symptom, name the box and the first file to open.

About 30 minutes. Sections 1–2 are the picture; 3–9 walk each box; 10–11 are how it changes and where bugs live; 12 is practice. Terms in dotted underline are in the Glossary; the compressed version of all of this is the Architecture Map.

1 The picture: five boxes

DreamCast (the app's name since v2.3, 13 Oct 2026; the repo, database and image keep the old warehouse-forecast name1) pulls data from your dwh catalog, keeps it in Postgres next to records it owns itself, computes every number on request from one primitive, and serves it to planners through a React app.

Two things about this picture are new since October, and both change how you debug:

  • Store is "mirror + record". DreamCast is now the source of truth for ranging, both SKU statuses, seller SKUs and the Amazon case pack (sku_range), the weekly replenishment orders and their audit trail, planned demand adjustments, the promo calendar and compliance cases. Data flows both ways: you are due to read sku_range into Databricks.2
  • There is a second front door. An MCP server lives in the same process at /mcp, using the same services as the REST API.

What has not changed is the middle: projection.py is byte-for-byte the file it was on 1 October. Every feature since was added by changing its inputs.

Not a SQL warehouse. It auto-terminates, so a cold start takes minutes; sync step 0 probes it and waits if the probe was slow.

One process does everything. Web API, SPA files, the scheduler, the sync thread, the cache and (when enabled) MCP. That is why the image pins --workers 1 (Dockerfile:36): a second worker would fire the cron twice and split the cache in two.

The start command is the migration and seed runner. alembic upgrade head && python -m app.seed && uvicorn …. A broken migration or seed means the app never starts, and the pipeline is already green by then.

Postgres is a container, not RDS. The data lives in a Docker volume on the host. A shell on the host is reached through AWS SSM, not SSH.

3 Box 1 · Sync: how data arrives

The trigger is not a Databricks job or a host cron. It is an APScheduler job registered in FastAPI's startup hook (backend/app/main.py:40-41):4

scheduler = BackgroundScheduler(timezone="UTC")
scheduler.add_job(run_incremental_sync, "cron", hour="8,20", minute=0,
                  timezone="UTC", id="twice_daily_sync")

08:00 and 20:00 UTC is two hours after the Databricks NetSuite load, so each run reads fresh data (it was once a day at 12:00 UTC until 5 Nov 2026). Settings › Sync Now (POST /api/sync/trigger) runs the same function in a daemon thread.

The orchestrator, run_incremental_sync (databricks_sync.py:2150-2218), is a flat list of function calls. Grouped by what they feed:5

The failure mode to remember

An "abort" step logs its error to sync_log and re-raises. The orchestrator stops there, before invalidate_cache(). So after a mid-run failure, cached pages keep showing the previous run's numbers, while any page that gets recomputed (new parameters, an admin save) mixes refreshed and stale tables. Also: the sidebar's "Last sync 3h ago" reads the most recent completed step of any run, so a run that died at step 9 still looks fresh. Check Settings' step list, not the sidebar.

Every source table is a cross-repo contract. All but one are yours in ltd-dbx-asset-bundle; the shipping master (dwh.shipping.master_ns_jas_inbound_shipment_pos) is owned by the shipping side. Rename or retype a column there and that step fails, and for an abort step, so does the rest of the run. Lesson 6 takes the sync apart.

5 Box 3 · Engine: one primitive, three inputs

Until September 2026 the app had six separate projection loops with six ideas of demand, and their numbers sat side by side "as though they agreed. They did not." Matt replaced them with one module. Its docstring opens: "Every cover figure, order quantity and urgency band in the app is a reading of the same thing."7

opening stockstock_cover.get_physical_soh DemandSeriesdemand.location_demand graded arrivalsinbound_grading projection.project() a readingweeks_of_cover · deficit_against · min_point · gap_before policycaps · case packs · range gates · holds · launches review rulesflag lines, never move a quantity

The whole loop, backend/app/services/projection.py:279-289:7

    points: list[ProjectionPoint] = []
    running = float(opening_soh)
    for i, p in enumerate(periods):
        items = by_period.get(i, [])
        arrived = sum(a.quantity for a in items)
        demand = p.demand
        closing = running + arrived - demand          ← nothing is floored
        points.append(ProjectionPoint(p, running, arrived, demand, closing, items))
        running = closing

    return Projection(float(opening_soh), points, dropped)

A running balance, nothing more. The engines differ in what they feed it and which question they ask of the result:

  • Cover pages (Dashboard, All SKUs, Alerts, Out of Stock, Velocity) ask weeks_of_cover(cap=52).
  • Quantity engines ask deficit_against(floor, from_period=…): Replenishment (fba_replenishment.py), Transfers (transfers.py) and Factory Buy (factory_buy.py, now stepped over LTD retail weeks).
  • Policy sits on the reading, never inside the loop: cap at what the source can spare, round to cases (case_packs.resolve), drop SKUs not ranged for the route (sku_range), zero a compliance hold, swap in a launch quantity.
  • Review rules (replenishment_rules.py, transfer_rules.py, factory_buy_rules.py) flag a line "to look at more closely" with a reason. By design they never change a quantity.

The design rule, "policy goes in the inputs, never in a forked loop", is why the primitive survived two months of features untouched. When a number changes, look at the inputs first: that's where every rule since October went (the demand series alone grew from about 800 to 1,234 lines).

6 Trace one number through all five boxes

A Dashboard row (US market) shows a bar and a figure under Riverside, say 6.5 wk (synthetic). Top to bottom:8

  1. UI frontend/src/pages/Dashboard.tsx:80-98: a useEffect that re-runs when market changes calls fetchStockCover(). The cell renders row.warehouse_totals[wh].weeks_of_cover (:368); the bar's width is woc / 26 (:371), full at 26 weeks though the figure caps at 52.
  2. UI api/dashboard.ts:33-36 issues GET /dashboard/stock-cover; the axios interceptor in api/client.ts:32-39 appends ?market=US from the market store, and the next one (:41-64) attaches the Entra ID token as Bearer.
  3. API routers/dashboard.py:105 stock_cover. Its market comes from Depends(get_market_param), which first runs get_current_user (validate the token, apply the reader scope). It builds a cache key prefixed with CALC_BASIS_VERSION (:116) and returns the cached payload if one exists, which after a sync is the normal case because the warm-up step filled it.
  4. Engine Opening stock: stock_cover.get_physical_soh reads free to sell (inventory_levels.quantityavailable) per warehouse and SKU.
  5. Engine warehouse_velocity.get_batch_seasonal_woc (:310) builds demand (:374) and arrivals (:376), then _cover_for (:416-449) runs project(soh, series.weekly_periods(today, 52), arrivals, early_arrivals="credit") and reads weeks_of_cover(cap=52).
  6. Engine Demand: demand.location_demand (:1140) asks demand_channels_for_location (:1059). Riverside (124) is the US hub, so the answer is ALL_CHANNELS: every US sale, with one-off orders split off and planned adjustments attached, read from daily_sales.
  7. Engine Arrivals: inbound_grading.graded_incoming_by_location (:528) grades lots from the shipping master first (inbound_shipment_po), then open POs the master doesn't describe, Amazon shipment lots, and open transfer orders.
  8. Store daily_sales, unique on (date, country, channel, sku, revenue_type); inventory_levels; inbound_shipment_po.
  9. Sync sync_daily_sales (databricks_sync.py:157) upserts from dwh.netsuite.gold_netsuite_daily_sales_by_customer, re-pulling the last 7 days, relabelling each market's Amazon FBM customer as channel FBM.
  10. Source your gold table. Its grain and column names are now part of DreamCast's contract.
What the trace tells a maintainer

A "wrong" cover has exactly three suspects: opening stock (inventory_levels), the demand series (its hover label says which basis it used), or the graded arrivals. And a fourth that isn't a calculation at all: the cache served something computed before the data or the rules changed.

7 Trace one write, and the loop it closes

Reads are half the system. The other half is planners acting on the numbers, and the result coming back through the sync. The weekly Amazon order shows it best:9

  1. UI. On Replenishment (/fba, ReplenishmentOrder.tsx, the biggest page) a planner steps a Ship Qty by one case. The page calls PUT /api/dashboard/replenishment-orders/{id}/items/{sku}.
  2. API. routers/dashboard.py:1307 checks the user, the market, and that they are an editor.
  3. Engine. replenishment_orders.adjust_item checks the order's stage, sets the quantity, clears any approval tick, re-runs the auto-approval rules on that line, and writes an audit event to replenishment_order_event.
  4. Store. The order is part of the record. No cached page reads orders, so nothing is invalidated.
  5. Outside DreamCast. An approver approves; the planner exports one file per transfer order plus a Send to Amazon manifest, and raises the TOs in NetSuite.
  6. Sync. The next run's transfer_orders step brings those TOs back from your dwh; grading dates them ship date + 3 weeks (Riverside → Amazon), and next week's recommendation nets them off.

That loop is the system. A recommendation that "keeps asking for the same stock" usually means the loop broke somewhere: the TO wasn't raised, the sync failed, or grading didn't count it.

8 Box 4 · API: two front doors

REST. main.py:91-94 mounts four routers under /api/, FastAPI's standard APIRouter layout:10

RouterWhat it serves
authGET /me, and a dev-only login for local work.
dashboardEvery page read (cached ones: stock-cover, alerts, summary, transfers, overstock, fba-replenishment, factory-buy, inbound, product-performance, amazon-stock-gap, range-exceptions) and the replenishment-order read/write API.
adminUsers, SKU master, statuses, FBA config and promos, range, launches, reservations, compliance cases, demand adjustments.
syncTrigger, progress, status, last sync, data overview.

A handler is thin: resolve the user and market, check the cache, call a service, wrap the result in a Pydantic schema from schemas/, cache it. Two things bite here. A field a service returns but the schema doesn't declare is silently dropped. And the cache is a dict in the process's memory with no TTL: it is cleared at the end of a successful sync, by an admin change that affects it, or by a restart, and by nothing else. Every key is prefixed with CALC_BASIS_VERSION (services/cache.py:20); the release rule is to bump it in the same commit as any projection, velocity or grading change, so entries computed under the old rule can never be served again.

MCP. backend/app/mcp/ is a FastMCP server mounted in-process at exactly /mcp, and only when the MCP_ENABLED setting is true (main.py:106-114).11 It is a second front door onto the same services: six read tools (markets, orders, one order, a SKU's replenishment preview, stock cover, transfer recommendations) and two write tools (adjust and approve order lines). Writes are preview then confirm: call with confirm=false to get a preview and a change_token that fingerprints the batch; call again with the token, and if anything drifted in between, nothing is applied. Each write lands in the same audit table with source mcp. Whether it is switched on in production is an ops decision recorded in the repo's prod-ops skill; check there rather than assume.

9 Box 5 · UI: the React app

React will be new; for now you only need its shape.12

  • Routes are declared in frontend/src/App.tsx:123-155, one per file in pages/, all wrapped in ProtectedRoute (signed in? has a role? a reader on an allowed page?) and Layout (the sidebar).
  • The menu is navGroups in components/Layout.tsx:626: Dashboard; Operations (Replenishment, Transfers, Inbound, Compliance); Merch planning (Factory Buy, Range, Alerts, Out of Stock, Overstock, Stock Review, All SKUs); Analysis (Velocity, Amazon Stock Gap, FBA/FBM, Product Perf, YoY); Settings. The same file holds the user-facing CHANGELOG, whose first entry is the version shown in the sidebar.
  • Data: each page keeps its own state and fetches in a useEffect with market in its dependency list, so switching market refetches. No data-fetching library.
  • The client (api/client.ts) adds ?market=, the Bearer token, a single retry on 401, and a toast on any failed save.
  • Types in types/index.ts are hand-copied from the backend schemas. No code generation, so a new field is two edits.
Python bridge

Read a page as a function that returns HTML, re-run whenever its state changes. useState is a variable that triggers that re-run when set; useEffect(fn, [market]) is "run fn after rendering, and again whenever market changes", like a callback keyed on a parameter. Lesson 8 takes one page apart line by line.

10 Who can see what, and where: auth, roles, five markets

Sign-in. The SPA signs in with Microsoft Entra ID through @azure/msal-browser and sends the ID token as a Bearer token. The backend validates it against Entra's published keys (middleware/auth.py). The first time someone from LTD signs in, they are created as a reader on every market.13

viewerEvery page except Overstock and Settings; no writes.

is_approverA flag, not a role: may tick lines, approve and unlock the weekly order.

Markets. users.markets is a list. The get_market_param dependency takes ?market= (or the user's first market), refuses a market the user doesn't hold (403) or that doesn't exist (400), and hands the handler a clean market code. Every table holds every market; services filter by country, location or a market column, and every service function defaults to market="US", so a call that forgets market=market quietly computes US.

11 How a change reaches production

push to main Bitbucket Pipelinesdocker build (SPA + Python) ECRtagged commit SHA + latest SSM send-commandscripts/deploy.sh compose up -don the host migrate → seed → serve

About 3–5 minutes from push to live, with a short outage while the container restarts and runs Alembic.15 The pipeline builds and ships; it does not run Python checks. The gates are the ones you run before pushing, from the repo's release skill:

  1. A user-facing entry at the top of CHANGELOG in Layout.tsx, and the developer history in the root CHANGELOG.md.
  2. For any projection, velocity or grading change: the harness (backend/app/tools/compare_projections.py dump before and after, then compare) and a CALC_BASIS_VERSION bump.
  3. npx eslint src/ && npm run build; python -m compileall -q app; a linear migration chain (check the head on main before numbering).
  4. After deploy: recalculate the current weekly order; Sync Now if a Databricks-fed table or a market was added.

There are no git tags; the version of record is the sidebar CHANGELOG (2.26 today). Rollback is revert-and-push, or re-tag an older image as latest and compose up. Migrations only go forward in practice. Lesson 9 is the deploy.

13 Practice: make it stick

Exercise A · Retrieval

Which box does each path belong to?

Exercise B · A maintainer's day

This morning's sync failed at step 14, inbound_shipments. A planner says the Dashboard looks exactly like yesterday, but a SKU she opened in Velocity shows today's stock. Why do the two pages disagree?

The cache was never invalidated. Step 14 is an abort step, so the orchestrator stopped before invalidate_cache() and the warm-up. Dashboard (/stock-cover) serves its cached payload from the last good run. Velocity's detail endpoints are uncached, so they recompute from tables that steps 1–13 already refreshed: mixed-age data. Nothing reads Databricks at request time, and there is no rollback. First move: the step's error in Settings, then sync_inbound_shipments in databricks_sync.py.
Exercise C · A maintainer's day

A planner set a SKU's Amazon FBA range call to "no" in DreamCast last week. Merch's file, synced every run, still says "yes". Which table decides what the replenishment engine does?

sku_range, the record DreamCast owns. The merch file is mirrored into sku_market_status and only seeds sku_range where a call is still undecided: the file seeds, a decision wins. amazon_range is a dead table kept for history, and dwh.merch.best_seller_sku_status is the source of the mirror, not something the engine reads.
Exercise D · A maintainer's day

A bad PO row came through from NetSuite, and you corrected it with SQL in the prod database over SSM. An hour later the Dashboard still shows the cover computed from the bad row. Click the fix.

bump the CHANGELOG version, then redeploy everything re-run alembic upgrade head inside the container restart the app container to clear memory edit frontend types to match the row
Exercise E · A maintainer's day

The pipeline went green, but the site returns 502 and never recovers. What runs first when the new container starts, and so is the first suspect?

alembic upgrade head. The start command is alembic upgrade head && python -m app.seed && uvicorn … (Dockerfile:36), so a failing migration stops the chain before the web server ever starts, then the seed, then an import error in uvicorn. The pipeline can't catch any of these: it builds the image, it doesn't run it. Read the container logs over SSM.
Exercise F · Draw it from memory

On paper: draw the five boxes with Infra around them, then the Riverside trace from the bar down to dwh. Then check one hop: what does inbound grading read first?

inbound_shipment_po, the shipping master (dwh.shipping.master_ns_jas_inbound_shipment_pos), first source since v2.18. Open POs count only where the master doesn't describe them; amazon_fba_inbound is retired. The full chain:
Dashboard.tsx bar → fetchStockCover → GET /api/dashboard/stock-cover?market=US → get_current_user + get_market_param → cache hit? → get_batch_seasonal_woc → _cover_for → project(…, early_arrivals="credit") → weeks_of_cover(cap=52)
inputs: opening = inventory_levels · demand = hub → all channels → daily_sales ← step 1 ← gold_netsuite_daily_sales_by_customer · arrivals = shipping master, then POs, Amazon shipment lots, TOs.
