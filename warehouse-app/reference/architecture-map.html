2 The engine, as one picture

Every cover figure, order quantity and urgency band follows one recipe: opening stock + a DemandSeries + graded arrivals → projection.project → a reading, then policy, then review rules.

 daily_sales ─► monthly_velocity ─► demand.channel_demand ─────────┐   one-offs split off,
 daily_soh ──► monthly_warehouse_velocity ─► demand.warehouse_demand ┤   level rules, planned
                                                                     ▼   adjustments attached
              demand.location_demand  (basis per location from market_config)
                                                                     │ DemandSeries
 inbound_shipment_po (shipping master, first) · open POs it doesn't  │
 describe · Amazon TO shipment lots · open TOs                       │
        ─► inbound_grading ─► arrivals (graded, dated, weighted)     │
                                                                     ▼
 opening stock (inventory_levels.quantityavailable; Amazon fulfillable) ─► project(...)
                                                                     ▼
   readings: weeks_of_cover(cap 52) · deficit_against(floor, from_period) · min_point · gap_before
                                                                     ▼
   policy:   source caps − e-com reserves · case packs · range gates (sku_range)
             · compliance holds · launch overrides
                                                                     ▼
   review rules (flag, never move a quantity): replenishment_rules · transfer_rules · factory_buy_rules

projection.py has not changed since 0b134ca (1 Oct 2026). "Policy goes in the inputs (periods, arrivals, floor), never in a forked loop." A few figures are still plain division (stock ÷ trailing rate); the register is forecast-calculations.md:683-727.

10 Deploy and release

push to main Pipelines: docker build ECR (:sha, :latest) SSM: pull + compose up -d alembic → seed → uvicorn
  1. User-facing entry at the top of CHANGELOG in Layout.tsx (sidebar version) + developer entry in CHANGELOG.md.
  2. Engine change: harness dump before and after, compare; bump CALC_BASIS_VERSION ("YYYY-MM-DD.N").
  3. npx eslint src/ && npm run build; python -m compileall -q app; linear migration chain; a sku_range column rename or drop also breaks the Airbyte feed into dwh.dreamcast.
  4. Push; watch the pipeline; confirm live by a distinctive new string in the served JS bundle.
  5. After deploy: recalculate the current weekly order; Sync Now if a fed table or market was added.
  6. Rollback: revert and push, or re-tag an older :sha image as latest and compose up -d. Migrations go forward only in practice.

11 The maintainer's rules

1 · No test suite: the harness is the gate, and main is production. The pipeline builds and ships; it never runs Python. A runtime error ships too.

2 · Every service defaults market="US". Pass market=market on every call, or a non-US market silently computes US.

3 · The cache has no TTL and lives in process memory. Bump CALC_BASIS_VERSION with any rule change; SQL fixes and out-of-process syncs need a restart or Sync Now.

4 · The file seeds, a decision wins. The sync never overwrites a decision stored in sku_range. And sku_range is itself a source now: Airbyte reads it into dwh.dreamcast, so its columns are a contract.

5 · One worker, always. The scheduler, cache and rate limiters assume a single process.
